Scopes and owned instances (IOwned) in Quick.IOC

A guide to how the container now controls lifetimes "per scope", written for those who already use Quick.IOC with AsTransient and AsSingleton. First the concept and the usage. Then the story of one request, told from beginning to end: where the scope is born, how it reaches each dependency, how an IOwned<T> creates a second scope, what keeps each instance alive, and how the scopes are released.

The examples come from samples/delphi/QuickIOC/ScopedAndOwned, which has the same application in Horse (one scope per request) and in VCL (one scope for the whole application, which the screens use by default), with no database.

1. The problem: transient and singleton are not enough

Until now Quick.IOC offered two lifetimes:

LifetimeThe container hands out
AsTransienta new instance on every resolution
AsSingletonthe same instance for the whole application

Think of an API that saves a customer and an audit entry. The service uses two repositories, and both must work on the same connection and in the same transaction: if saving the customer is rolled back, the audit entry must be rolled back too. The connection with its transaction is the "unit of work" (IUnitOfWork).

  • With AsTransient, each repository gets a unit of work of its own: two connections, and the transaction of one does not apply to the other.
  • With AsSingleton, every request shares the same unit of work: the transaction of one request mixes with another's, and one connection is used by several threads.

What is needed is something in between: one instance per request. Within the request, everyone gets the same unit of work; another request gets another one. That is what AsScoped does: the "scope" is the boundary (a request, a screen, a task) within which the instance is shared.

Before this change, AsScoped already existed in the API, but the container had no scope object: an AsScoped registration was resolved as transient. Now the scope is an object, TIocScope.

2. Using scopes

The registration sets the lifetime of each service. This is what the sample does, in Common/ScopedAndOwned.Registration.pas:

  // ---- SINGLETON: one instance for the whole application ----------------------------------
  aContainer.RegisterInstance<IActivityLog>(aLog).AsSingleton;
  aContainer.RegisterType<IFakeDatabase, TFakeDatabase>.AsSingleton;

  // ---- SCOPED: one instance per scope ------------------------------------------------------
  // The scope is the request's (Horse), the application's or a screen's own (VCL), or an IOwned's
  aContainer.RegisterType<IUnitOfWork, TFakeUnitOfWork>.AsScoped;
  aContainer.RegisterType<ICustomerRepository, TCustomerRepository>.AsScoped;
  // also registers IOwned<IAuditRepository> (AutoRegisterOwned, True by default)
  aContainer.RegisterType<IAuditRepository, TAuditRepository>.AsScoped;

  // ---- TRANSIENT: a new instance on every resolution ---------------------------------------
  aContainer.RegisterType<IOwnedAuditService, TOwnedAuditService>.AsTransient;
  aContainer.RegisterType<ISameTransactionAuditService, TSameTransactionAuditService>.AsTransient;

The boundary is set by whoever creates and frees the scope. In Horse, a middleware opens a scope when each request starts and frees it when the request ends (Horse/ScopedAndOwned.ScopePerRequest.pas):

procedure ScopePerRequest(Req: THorseRequest; Res: THorseResponse; Next: TProc);
var
  scope: TIocScope;
  session: TScopeSession;
begin
  scope := GlobalContainer.CreateScope;
  try
    session := TScopeSession.Create; // owned by Req.Sessions; the scope is owned by this middleware
    session.fScope := scope;
    Req.Sessions.SetSession(TScopeSession, session);
    try
      Next();
    finally
      session.fScope := nil;
    end;
  finally
    // Free releases every instance of the scope, and raises again the first exception raised by
    // their destructors. The response is already built at this point: report it, do not raise it
    try
      scope.Free;
    except
      on E: Exception do
        Writeln(ErrOutput, 'Error releasing the request scope: ', E.ClassName, ': ', E.Message);
    end;
  end;
end;

And the route resolves from the request's scope (Horse/ScopedAndOwned.Routes.pas):

  service := RequestScope(Req).Resolve<IOwnedAuditService>;
  Save(service, Req, Res);
  // releasing the service releases its IOwned, and with it the IOwned's scope
  service := nil;

In VCL: one scope for the whole application

In the VCL sample, the first scope belongs to the application: it is born in the .dpr, before the main form, and is freed at the end, after every form. By default, every screen uses this scope and therefore shares the same unit of work, which plays the part of the application's open connection (VCL/ScopedAndOwnedVcl.dpr):

  // scope A: created with the application, before any form; every form uses it by default
  CreateApplicationScope;
  Application.CreateForm(TMainForm, MainForm);

The scope lives in a component of Application, created before any form (VCL/ScopedAndOwned.ApplicationScope.pas):

type
  //owned by Application and created before any form: Application frees its components in reverse
  //order of creation, so the scope is freed after every form, when no form uses it anymore
  TApplicationScopeHolder = class(TComponent)

The main form, like any other, resolves from it, and that opens the application's connection right at startup (VCL/ScopedAndOwned.MainForm.pas):

  fConnection := ApplicationScope.Resolve<IUnitOfWork>;

A screen has two constructors: the default one uses the application's scope (or the scope it is given), and the other creates a scope of its own, disconnected from the application's scope, freed when the screen closes (VCL/ScopedAndOwned.ScreenForm.pas):

constructor TScreenForm.CreateFor(aOwner: TComponent; aKind: TAuditKind; aScope: TIocScope);
begin
  if aScope = nil then aScope := ApplicationScope;
  fScope := aScope;
  inherited Create(aOwner);
  Setup(aKind);
end;

constructor TScreenForm.CreateWithOwnScope(aOwner: TComponent; aKind: TAuditKind);
begin
  fScope := GlobalContainer.CreateScope;
  fOwnsScope := True;
  inherited Create(aOwner);
  Setup(aKind);
end;
  // released first: the service, and for akOwned its IOwned with the IOwned's scope
  fService := nil;
  // only a scope of its own is freed here: the application's scope lives as long as the application
  if fOwnsScope then fScope.Free;

The result, with one screen of each kind open:

The three ways for a part of the system to get a unit of work of its own, leaving the application's connection:

Who decidesHowWhen the new scope is freed
the screenCreateWithOwnScopewhen the screen closes
the serviceasks for the dependency as IOwned<T> (section 7)when the service releases the IOwned

Usage in short: CreateScope opens, scope.Resolve<T> resolves within it, scope.Free releases everything created in it. Whoever calls CreateScope owns the scope and must free it, and always before the container.

3. The story of one request

To understand what happens inside, let us follow a single request of the Horse sample, POST /owned?name=Ann&rollback=true, from beginning to end. In VCL the story is the same; only the first scope changes: instead of one per request, there is one for the whole application, which the screens use by default.

The service of this route is TOwnedAuditService. It saves the customer and the audit entry, and asks for the audit repository as IOwned<IAuditRepository> (why is explained in step 4):

constructor TOwnedAuditService.Create(aUnitOfWork: IUnitOfWork; aCustomers: ICustomerRepository;
  aAudit: IOwned<IAuditRepository>);
begin
  inherited Create;
  fUnitOfWork := aUnitOfWork; // from the scope that resolved the service
  fCustomers := aCustomers;   // from the same scope: the same unit of work
  fAudit := aAudit;           // a scope of its own: another unit of work
end;

Two scopes take part in this request. The rest of the guide calls them:

  • Scope A, the request's: the middleware creates it when the request arrives and frees it when the request ends. In the VCL sample, it is the application's scope, which the screens use by default (or the own scope of a screen opened with CreateWithOwnScope). It is the first scope, where the resolution starts.
  • Scope B, the IOwned's: it is born during the resolution of the service, because the service asks for an IOwned, and it is freed when the service releases that IOwned.

The whole timeline:

This is what the sample's console shows for that request (the comments on the right are not printed):

4. Step 1: scope A is born

The middleware calls CreateScope. Creating a scope is cheap: only the object is created, and nothing is built until the first resolution.

function TIocContainer.CreateScope: TIocScope;
begin
  Result := TIocScope.Create(fResolver);
end;

The scope is a simple object: the resolver it uses, two "registration → instance" tables and two lists with the order of creation. Declaration in Quick.IOC.pas:

  TIocScope = class
  private
    fResolver : TIocResolver;
    fReleasing : Boolean;
    fInterfaces : TDictionary<TIocRegistration, IInterface>;
    fObjects : TDictionary<TIocRegistration, TObject>;
    fCreated : TList<IInterface>;
    fCreatedObjects : TList<TObject>;
    procedure CheckAlive;
    function GetOrCreate(aReg : TIocRegistration; aServiceType : PTypeInfo) : TValue;
  public
    constructor Create(aResolver : TIocResolver);
    destructor Destroy; override;
    function Resolve<T>(const aName : string = ''): T; overload;
    function Resolve(aServiceType: PTypeInfo; const aName : string = ''): TValue; overload;
  end;
FieldWhat it is for
fInterfacesthe instance of each (interface) registration already created in this scope: the "does it exist?" lookup
fObjectsthe same for class registrations (RegisterInstance<TClass>), which are not interfaces
fCreated, fCreatedObjectsthe order in which the instances were created, to release them in reverse order
fReleasingset when Free starts: from then on the scope refuses to resolve

The key of the tables is the registration (TIocRegistration), not the type. Each RegisterType creates a registration; the scope keeps at most one instance per registration.

Later, in step 4, scope B will be created by the same CreateScope. Both are identical TIocScope objects: what tells them apart is only who created them and who holds them.

5. Step 2: the resolution carries the scope along

The route asks scope A for the service: RequestScope(Req).Resolve<IOwnedAuditService>. The service asks for IUnitOfWork in its constructor, and so does TCustomerRepository. How does the container know that these units of work must come from scope A?

There is no "current scope" stored anywhere: no global variable, no stack, no counter. The scope travels as a parameter, aScope, through the whole resolution chain. Each step receives aScope and passes it on to the next.

aScope is always the scope the resolution started from:

Who askedaScope
the route, with RequestScope(Req).Resolve; in VCL, the screen, with fScope.Resolvescope A (in VCL, the application's or the screen's own)
the IOwned's delegate, during step 4scope B
someone with GlobalContainer.Resolve, with no scopenil

In step 2 of our story, aScope is scope A:

The entry point is the scope's Resolve, which passes itself (Self) to the resolver: this is where scope A enters the chain.

function TIocScope.Resolve(aServiceType: PTypeInfo; const aName: string): TValue;
begin
  CheckAlive;
  Result := fResolver.Resolve(aServiceType,aName,Self);
end;

The "old" Resolve, with no scope, still exists and passes nil: it is what the root container uses.

function TIocResolver.Resolve(aServiceType: PTypeInfo; const aName : string = ''): TValue;
begin
  Result := Resolve(aServiceType,aName,nil);
end;

When building through RTTI, each constructor parameter is resolved with the same aScope (excerpt of TryInvoke, inside TIocResolver.CreateInstance):

        try lVal := Resolve(lParam.ParamType.Handle, lName, aScope);
        except on EIocResolverError do Exit; // required dep not found
        end;

That is how the dependency of a dependency, at any depth, lands in the same scope: each recursive call receives the same aScope. There is nothing to "discover": the scope is an argument.

6. Step 3: each dependency, by its lifetime

For each dependency, TIocResolver.Resolve finds the registration (the last one registered for the type and the name) and decides by its lifetime. In step 3, aScope is scope A:

In our request:

  • IOwnedAuditService is transient: it is built on the spot, with the same aScope (scope A), and it is not kept in the scope.
  • IUnitOfWork is scoped and aScope is scope A: A creates UnitOfWork 1 and keeps it.
  • ICustomerRepository is scoped: A creates the repository. Its constructor asks for IUnitOfWork again, and A returns the same UnitOfWork 1, which it already keeps.

The new part of Resolve is the scoped branch, right after finding the registration:

  //scoped: one instance per scope, created and released by the scope
  if reg.IsScoped then
  begin
    if aScope <> nil then Exit(aScope.GetOrCreate(reg,aServiceType));
    if fValidateScopes then
      raise EIocScopeError.CreateFmt('Scoped service "%s" resolved outside a scope. Resolve it from a TIocScope ' +
        '(TIocContainer.CreateScope), not from the root container nor as a dependency of a singleton; or set ' +
        'ValidateScopes := False to keep the previous behaviour (resolved as transient).',[aServiceType.Name]);
    //ValidateScopes = False: previous behaviour, built below as a transient
  end;

And, on the singleton path, the line that "forgets" the scope before building (the reason is in section 12):

    //dependencies of a singleton are resolved with no scope: a scoped one would be captured for
    //the whole application lifetime, so it raises EIocScopeError instead
    aScope := nil;
  end;
  //instance not created yet or needs to be created (transient)
  Result := BuildValue(reg,aServiceType,aScope);

GetOrCreate: "the same instance within the scope"

The scope looks the registration up in its table. If it is not there, it has the resolver build it, passing itself as the scope (for the dependencies), and keeps the result in the table and in the creation list:

function TIocScope.GetOrCreate(aReg: TIocRegistration; aServiceType: PTypeInfo): TValue;
var
  cached : IInterface;
  intf : IInterface;
  obj : TObject;
begin
  //the single place where the scope creates and keeps instances: reached from Resolve, but also
  //from dependency chains and IOwned
  CheckAlive;
  if aReg is TIocRegistrationInterface then
  begin
    if not fInterfaces.TryGetValue(aReg,cached) then
    begin
      //dependencies are resolved within this same scope
      cached := fResolver.BuildValue(aReg,aServiceType,Self).AsInterface;
      fInterfaces.Add(aReg,cached);
      fCreated.Add(cached);
    end;
    if cached.QueryInterface(GetTypeData(aServiceType).Guid,intf) <> 0 then
      raise EIocResolverError.CreateFmt('Implementation for "%s" not registered!',[aServiceType.Name]);
    TValue.Make(@intf,aServiceType,Result);
  end

BuildValue is the part of the old Resolve that builds the instance, moved out so the scope can use it too. It never keeps anything: the caller does (the scope, for scoped; the registration, for singleton). Note the second-to-last line of this excerpt: the delegate (DelegateTo) is called without the scope; only building through a constructor receives it. This detail is the key to step 4.

function TIocResolver.BuildValue(aReg: TIocRegistration; aServiceType: PTypeInfo; aScope: TIocScope): TValue;
var
  intf : IInterface;
  newInst : IInterface;
begin
  //builds a new instance, never caches: shared by Resolve and by the scopes
  if aReg is TIocRegistrationInterface then
  begin
    //if instance already set (RegisterInstance<TInterface>(obj)), use it directly
    newInst := TIocRegistrationInterface(aReg).Instance;
    if newInst = nil then
    begin
      //otherwise, create new instance from &Implementation
      if aReg.&Implementation = nil then raise EIocResolverError.CreateFmt('Implemention for "%s" not defined!',[aServiceType.Name]);
      {$IFDEF DEBUG_IOC}
      TDebugger.Trace(Self,'Building dependency: %s',[aReg.fIntfInfo.Name]);
      {$ENDIF}
      if Assigned(aReg.ActivatorDelegate) then newInst := aReg.ActivatorDelegate().AsInterface
        else newInst := CreateInstance(aReg.&Implementation,aScope).AsInterface;

7. Step 4: the service asks for an IOwned

The third parameter of the service's constructor is IOwned<IAuditRepository>. Why not simply IAuditRepository?

Within scope A, everyone gets the same UnitOfWork 1. Sometimes a part of the graph needs exactly the opposite: its own. In the sample, the audit entry must be kept even if saving the customer is rolled back (it is the proof that someone tried). If the audit repository used UnitOfWork 1, the rollback would take the audit entry with it. It needs another unit of work, outside the transaction.

IOwned<T> (inspired by Autofac's Owned<T>) solves this: the constructor asks for IOwned<T> instead of T, and the container resolves T in a new scope of its own, scope B, which lives as long as the IOwned<T> is referenced.

The two services of the sample use the same registrations; only the constructor changes. TSameTransactionAuditService, of the /same-transaction route, asks for the repository directly:

constructor TSameTransactionAuditService.Create(aUnitOfWork: IUnitOfWork; aCustomers: ICustomerRepository;
  aAudit: IAuditRepository);
begin
  inherited Create;
  fUnitOfWork := aUnitOfWork; // the three references point to the same unit of work
  fCustomers := aCustomers;
  fAudit := aAudit;
end;

The result, on the two routes:

With rollback=true, UnitOfWork 1 rolls back the customer, and UnitOfWork 2 has already written the audit entry. With TSameTransactionAuditService, everything is in UnitOfWork 1, and the rollback discards both.

The service keeps the IOwned, not only its Value. The reference to the IOwned is what keeps scope B alive (sections 10 and 11):

function TOwnedAuditService.Save(const aName: string; aRollback: Boolean): TSaveResult;
begin
  Result := SaveCustomer('OwnedAuditService', fUnitOfWork, fCustomers, fAudit.Value, aName, aRollback);
end;

8. Inside step 4: how IOwned creates scope B

The registration: done by RegisterType

IOwned<IAuditRepository> is a generic type, and Delphi cannot build a new generic type at runtime from IAuditRepository. That is why IOwned<I> is registered at the moment I is registered, while the compiler still knows the type:

function TIocContainer.RegisterType<TInterface, TImplementation>(const aName: string): TIocRegistration<TImplementation>;
begin
  Result := fRegistrator.RegisterType<TInterface, TImplementation>(aName);
  //IOwned<TInterface> must be registered here: generic types cannot be instantiated at runtime
  if fAutoRegisterOwned then RegisterOwned<TInterface>(aName);
end;

RegisterOwned<I> checks that I is registered and, if IOwned<I> does not exist yet for that key, calls AddOwned<I>. There is one IOwned per key (type and name): it resolves what Resolve<I> returns, so it also follows a registration of I added later.

procedure TIocContainer.RegisterOwned<TInterface>(const aName : string);
var
  named : string;
begin
  if not fRegistrator.IsRegistered<TInterface>(aName) then
  begin
    if aName.IsEmpty then named := ''
      else named := ' with the name "' + aName + '"';
    raise EIocRegisterError.CreateFmt('RegisterOwned<%s>: %s is not registered%s; register it first',
      [GetTypeName(TypeInfo(TInterface)),GetTypeName(TypeInfo(TInterface)),named]);
  end;
  //one IOwned per key: it resolves what Resolve<TInterface> returns, so it also follows a
  //registration added later
  if not fRegistrator.IsRegistered<IOwned<TInterface>>(aName) then AddOwned<TInterface>(aName);
end;

AddOwned<T> is the heart of the mechanism. It registers IOwned<T> as transient (each consumer gets its own) and with a delegate that does all the work:

procedure TIocContainer.AddOwned<T>(const aName : string);
var
  container : TIocContainer;
  regName : string;
begin
  container := Self;
  regName := aName;
  //transient: every consumer gets its own scope. Registered through the non-generic
  //RegisterType so it does not register an IOwned of IOwned<T>
  fRegistrator.RegisterType(TypeInfo(IOwned<T>),TOwned<T>,aName).ActivatorDelegate :=
    function : TValue
    var
      scope : TIocScope;
      owned : IOwned<T>;
    begin
      //independent scope: it does not see the consumer's scoped instances, only singletons
      scope := container.CreateScope;
      try
        owned := TOwned<T>.Create(scope,scope.Resolve<T>(regName));
      except
        //the resolution failure is what the caller must see: an exception raised while releasing
        //what was already created in the scope is dropped instead of hiding it
        try
          scope.Free;
        except
        end;
        raise;
      end;
      Result := TValue.From<IOwned<T>>(owned);
    end;
end;

Reading the delegate line by line, in our request:

  1. container.CreateScope: this is where scope B is born, like any other scope.
  2. scope.Resolve<T>(regName): resolves IAuditRepository in scope B. From here on, the aScope that travels down the chain (section 5) is B: AuditRepository asks for IUnitOfWork, and B creates UnitOfWork 2.
  3. TOwned<T>.Create(scope, ...): wraps the value and hands scope B over to the TOwned, which becomes its owner.
  4. If the resolution fails, scope B is freed right there, and the original error is the one raised.

Those who do not want the automatic registration turn AutoRegisterOwned off and call RegisterOwned<I> only where needed. RegisterOwned<I> also covers what RegisterType<I,T> does not: the non-generic RegisterType and RegisterInstance.

The resolution: the resolver "detects" nothing

How does the resolver notice that the IOwned<IAuditRepository> parameter needs a new scope? It does not. To the resolver, IOwned<IAuditRepository> is just another transient registration, whose delegate happens to create a scope:

The detail that makes it all work is in BuildValue (section 6): the delegate is called as aReg.ActivatorDelegate(), without scope A. The delegate has no way to see the consumer's scope and, therefore, creates its own. Scope B is independent of A by construction.

The only place where the resolver recognizes an IOwned explicitly is a configuration check, in TryInvoke: if the constructor asks for an IOwned<I> that was not registered, it is a registration error, never a reason to try another constructor:

        //IOwned<I> is asked for on purpose, for a scope of its own: without its registration this
        //is a configuration error, never a reason to try another constructor
        if IsOwnedType(lParam.ParamType.Handle) and
          not fRegistrator.Dependencies.ContainsKey(fRegistrator.GetKey(lParam.ParamType.Handle,lName)) then
          raise EIocRegisterError.CreateFmt('%s.%s asks for %s, which is not registered: call RegisterOwned or ' +
            'enable AutoRegisterOwned',[aCtor.Parent.Name,aCtor.Name,lParam.ParamType.Name]);

And IsOwnedType recognizes any IOwned<...> by its GUID, which is the same for every instantiation of a generic interface:

function IsOwnedType(aType : PTypeInfo) : Boolean;
begin
  //every IOwned<T> has the GUID of the generic declaration: what tells them apart from other
  //interfaces without knowing T
  Result := (aType <> nil) and (aType.Kind = tkInterface) and
    IsEqualGUID(GetTypeData(aType).Guid,GetTypeData(TypeInfo(IOwned<IInterface>)).Guid);
end;

9. Scope A and scope B: nested, but with no hierarchy

It is common to picture scopes as a tree: scope B would be a "child" of scope A, the container would know which level it is at, and a child scope would see the parent's instances. That is not how it works.

What does not exist:

  • a "parent scope" field in TIocScope;
  • a level or depth number;
  • inheritance of instances: scope B does not see A's UnitOfWork 1 (which is why it creates UnitOfWork 2, exactly the goal).

What does exist is a chain of references between objects. The service (resolved in scope A) holds the IOwned; the TOwned holds scope B; scope B holds its instances. If AuditRepository, inside scope B, asked for another IOwned<U>, a scope C would be born, held by it. The "depth" appears by itself, through the object graph:

To the container, the three scopes are siblings: each was created by CreateScope and knows only the resolver. What they share are the singletons, which belong to the registrations and not to a scope. The "nesting" lies in who holds whom, and that is what decides when each scope is freed: the subject of the next two sections.

10. What keeps each instance alive: the "increment and decrement"

The story is halfway through: the service has saved (step 5) and now everything must be released. Before steps 6 and 7, the question is: what keeps each instance alive, and what makes it die? Does the container count how many scopes exist, or how many times an instance was handed out?

The container has no counter: not of instances, not of scopes, not of levels. Delphi does the counting: every instance handed out as an interface is reference counted. Each variable, field or list that receives the interface adds 1 (_AddRef); each one that releases it subtracts 1 (_Release); when it reaches zero, the destructor runs. What the container does is hold references and release them at the right time.

That same count governs the two scopes of the story, in two different ways:

What the count decides
Scope Awhen each of its instances dies. The scope holds two references to each instance (in the table and in the list); the objects that received the instance hold others. It dies only when all of them are released.
Scope Bwhen the whole scope is freed. The service holds the IOwned; when the IOwned's count reaches zero, the TOwned is destroyed and frees scope B.

In scope A: the count of UnitOfWork 1

In scope B: the count of the IOwned

In step 4, the delegate handed the service an IOwned (the TOwned object), and the service kept it in its fAudit field: it is the only reference to it. In step 6, the route releases the service; the service, when destroyed, releases fAudit; the IOwned's count reaches zero, and the TOwned is destroyed. Its destructor frees scope B. Section 11 shows that destructor.

Three practical consequences:

  • A scope destroys nothing by force where interfaces are concerned: it releases its own references. If someone outside still holds the instance, it outlives the scope, out of its control. That is why the routes and screens of the sample release the service (service := nil, fService := nil) before scope.Free.
  • Class registrations (RegisterInstance<TClass>, no interface) are not reference counted: the scope owns them and destroys them with Free when released. Whoever still holds a pointer to them is left with freed memory.
  • Scope B lives as long as someone holds the IOwned, no more, no less. If the service were a singleton, scope B would live as long as the application; if it were scoped in A, B would be freed while A is freed. In the VCL sample, the screen holds the service: the IOwned's scope lives while the screen is open, even if the screen uses the application's scope.

11. Steps 6 and 7: releasing the scopes

In our request, the scopes go in this order: first B (step 6, when the route releases the service), then A (step 7, when the middleware calls scope.Free).

Step 6: TOwned frees scope B

TOwned<T> owns scope B. It keeps the scope and the value:

  TOwned<T> = class(TInterfacedObject,IOwned<T>)
  private
    fScope : TIocScope;
    fValue : T;
  public
    constructor Create(aScope : TIocScope; const aValue : T);
    destructor Destroy; override;
    function Value : T;
  end;

Being a TInterfacedObject, it dies when the last reference to the IOwned<T> is released (section 10). The destructor releases the value before freeing the scope (the value may point to instances of the scope), and frees the scope even if the value's destructor raises:

destructor TOwned<T>.Destroy;
begin
  //release the value before its scope: it may hold references to the scope's instances
  try
    fValue := Default(T);
  except
    //the scope is released anyway, so its instances do not leak; the value's exception is the
    //one raised (one raised while releasing the scope is dropped)
    try
      fScope.Free;
    except
    end;
    raise;
  end;
  fScope.Free;
  inherited;
end;

fScope.Free releases a scope like any other, as described below. The whole chain of steps 6 and 7:

Step 7, and the end of any scope: TIocScope.Destroy

The scope's destructor is the same for A and for B. It does four things, in this order:

destructor TIocScope.Destroy;
var
  i : Integer;
  firstError : TObject;
begin
  //from now on nothing is resolved from this scope, not even by the destructors of its instances
  fReleasing := True;
  //a destructor that raises must not stop the release of the others: the first exception is
  //kept and raised again once everything is released
  firstError := nil;
  //release in reverse order of creation: dependents go before their dependencies
  fInterfaces.Clear;
  for i := fCreated.Count - 1 downto 0 do
  begin
    try
      fCreated[i] := nil;
    except
      if firstError = nil then firstError := TObject(AcquireExceptionObject);
    end;
  end;
  fCreated.Free;
  fInterfaces.Free;
  //class (non-interface) scoped instances are owned by the scope
  fObjects.Clear;
  for i := fCreatedObjects.Count - 1 downto 0 do
  begin
    try
      fCreatedObjects[i].Free;
    except
      if firstError = nil then firstError := TObject(AcquireExceptionObject);
    end;
  end;
  fCreatedObjects.Free;
  fObjects.Free;
  inherited;
  if firstError <> nil then raise firstError;
end;

1. It closes the door (fReleasing := True). A destructor of an instance of the scope may try to resolve something from that same scope. With the door open, the scope would create a new instance while its lists are being destroyed. With it closed, CheckAlive answers with EIocScopeError:

procedure TIocScope.CheckAlive;
begin
  if fReleasing then
    raise EIocScopeError.Create('The scope is being freed: nothing can be resolved from it anymore ' +
      '(e.g. from the destructor of one of its instances).');
end;

2. Reverse order of creation. With constructor injection, a dependency is always created before whoever depends on it: to build CustomerRepository, the container first resolves the UnitOfWork. In scope A's fCreated list, therefore, UnitOfWork 1 comes first. Walking the list back to front, the dependents go first, and the dependency goes last, when nothing else in the scope needs it.

3. A destructor that raises does not stop the others. Each release is inside a try/except; the first exception is kept (AcquireExceptionObject, which takes it out of the exception mechanism so it is not destroyed), and the other instances go on being released. Without this, a faulty destructor would leave every following instance alive forever.

4. It raises again at the end. After releasing everything and destroying its own lists, the scope raises the first exception again: the error does not vanish, and the other instances are released. Only the memory of the scope itself and that of the instance whose destructor raised are lost, because a destructor that raises skips releasing the object's memory (FreeInstance). That is why the sample's middleware catches the exception of scope.Free and reports it: at that point the response is already built.

12. And when there is no scope? ValidateScopes and the captive dependency

The story is over, but one case is left: what happens if a scoped service is asked for outside a scope, with aScope = nil?

  • From the root container (GlobalContainer.Resolve<IUnitOfWork>): there is no scope to keep the instance.
  • As a dependency of a singleton: the singleton lives as long as the application; if it received the UnitOfWork of a request, it would keep it after the request ended.

The second case is the more dangerous one, and it has a name: captive dependency.

That is why the singleton path clears the scope (aScope := nil, in section 6) before building: any scoped dependency of the singleton falls into the "outside a scope" case. And, with ValidateScopes = True (the default), outside a scope is an error: EIocScopeError, with a message that says what to do.

ValidateScopes := False restores the previous behaviour (a scoped service outside a scope built as transient), for those who already registered AsScoped and resolved from the root container:

    /// <summary>True (default): resolving a scoped service outside a scope (from the root
    /// container or as a dependency of a singleton) raises EIocScopeError.
    /// False: previous behaviour, a scoped service outside a scope is built as transient.</summary>
    property ValidateScopes : Boolean read fValidateScopes write fValidateScopes;

An IOwned resolved from the root container, or by a singleton, does not hit this error: it creates its own scope, and its scoped dependencies are born there.

Why EIocScopeError does not descend from EIocResolverError

Building through a constructor swallows an EIocResolverError from a parameter to try the next constructor (the except on EIocResolverError do Exit of section 5). If the scope error were an EIocResolverError, the container would give up on the right constructor and use another, for example the inherited TObject.Create, and the object would be born with the dependency nil, with no error at all. That is why EIocScopeError descends directly from Exception and always reaches the caller.

13. Practical rules and pitfalls

Free the scope before the container, when you can. The scope resolves through the container's resolver: resolving from a scope after the container is freed reads freed memory. Freeing the scope does not use the container.

Resolve nothing in destructors. A destructor of an instance of the scope that resolves from that same scope gets EIocScopeError (the door is already closed, section 11).

Release what came from the scope before freeing it. The scope only releases its own references (section 10). A variable that still holds the instance keeps it alive after the scope, and then it is destroyed at the wrong time, when the variable is released.

Beware of implicit temporaries. A chained call such as scope.Resolve<ILogger>.Log('x') creates a hidden reference that the compiler only releases at the end of the routine, after a scope.Free made in the middle of it. Use an explicit variable and set it to nil before Free, as the sample's routes do.

Keep the IOwned, not only its Value. Releasing the IOwned frees its scope. Interface instances held through the Value stay alive, but out of any scope's control; class instances of the scope are destroyed, and whoever still uses them reads freed memory.

A scope belongs to one thread at a time. The scope's tables have no lock. In Horse, each request has its own scope, and that is what makes it safe.

Create the singletons before serving several threads. Creating a singleton has no lock: if two threads ask for the same singleton for the first time at the same moment, both may build it. That is why the Horse sample calls GlobalContainer.Build before THorse.Listen: Build creates the singletons while the application still has a single thread.

A transient does not belong to the scope. A transient resolved within a scope receives the scope's scoped dependencies, but it is held by whoever resolved it, and it is not released by the scope.

Scoped inside a singleton is an error, on purpose. If a singleton needs something per request, it asks for an IOwned<T> (and controls when to release it) or receives the value as a parameter on each call.

An IOwned that was not registered is a configuration error. Asking for an unregistered IOwned<I> raises EIocRegisterError when the consumer is built, with the name of the constructor and what to do.
